# Linux support (plan, 2026-11-22)

Status: **Approved** (2026-11-22), with D1 (service) and D2 (live router test). Implemented in v0.4.0.

## What a test install on Debian 13 showed
On a Debian 13 (Trixie) x86_64 machine on the same network as the OpenWrt router, with a plain `git clone` of
v0.3.3 (`~/cf-test`, installed nothing system-wide):

- **Backend:** `python3 -m venv` and `pip install -r requirements.txt` work. **All 81 backend tests pass**,
  including the 9 router-gate tests that need `/bin/sh` and always error on native Windows.
- **Frontend:** `npm ci`, all 40 tests and `npm run build` work on Debian's own **Node 20.19.2**. Vite 7 needs Node
  20.19+ or 22.12+, so the README's "Node 22.12+" is stricter than it needs to be.
- **Running it:** in demo mode the page, assets and API all answer, and `backend.launcher` detects a running copy.

So the application is already cross-platform. What's Windows-only is the four helper scripts
(`setup.ps1`, `start.ps1`, `test.ps1`, `connect-router.ps1`) and `Start Dashboard.cmd`.

## Changes

### L1. Shell versions of the helper scripts (POSIX `sh`, Bash where needed)
| New | Does the same as | Notes |
| --- | --- | --- |
| `scripts/setup.sh` | `setup.ps1` | Checks for Python 3.11+ with `venv`, and Node 20.19+ or 22.12+ with npm. If something is missing, it prints the exact `apt`/`dnf` command and **doesn't run sudo itself**. Then it creates `.venv`, installs the requirements, and runs `npm ci` and `npm run build`. |
| `scripts/start.sh` | `start.ps1` | Runs `backend.launcher`. If a copy is already running, it says so (and opens the browser with `xdg-open` when there is a desktop). Otherwise it starts uvicorn on 127.0.0.1:8765 in the foreground. |
| `scripts/test.sh` | `test.ps1` | Backend unittest, frontend tests and build. |
| `scripts/connect-router.sh` | `connect-router.ps1` | The same five steps: (1) router address (default from `ip route`), (2) a dedicated key `~/.ssh/cypress_forge_collector`, (3) the installer generated by `backend.cli router-installer`, sent over one password SSH session, (4) `backend.cli configure`, (5) the verify checks plus "arbitrary command refused". The same exit codes and messages. |

The scripts are marked executable in git, use LF line endings (forced in `.gitattributes`, so a Windows checkout can't
break them), and are checked with `shellcheck` where available.

### L2. Optional background service (systemd user unit)
- `scripts/install-service.sh` writes `~/.config/systemd/user/cf-network-dashboard.service`, which runs uvicorn from
  the project folder on 127.0.0.1:8765 and restarts on failure.
- It enables the service (`systemctl --user enable --now`) and offers `loginctl enable-linger` so the dashboard keeps
  running when you're not logged in. That one step needs `sudo`, so the script prints the command rather than
  running it.
- `scripts/uninstall-service.sh` reverses it.
- This is the Linux equivalent of keeping the Windows console window open, and it suits always-on machines such as a
  home server.

### L3. Docs
- **README:**
  - The requirements say "Windows 10/11 or Linux (tested on Debian 13)", and Node "20.19+ or 22.12+".
  - There's a Linux section with `./scripts/setup.sh`, `./scripts/start.sh`, `./scripts/connect-router.sh` and the
    optional service.
  - The note about the router-gate tests erroring on Windows stays.
- **`docs/ROUTER-ACCESS.md`:** adds the Linux command next to the PowerShell one.
- **CHANGELOG:** v0.4.0 (a new platform, so a minor version bump).

### L4. CI (small)
- A GitHub Actions workflow runs `scripts/test.sh` on `ubuntu-latest` for every pull request.
- That gives the public repo a green check, and the router-gate tests finally run somewhere automatically.

## Testing
1. **On the Debian machine, from a fresh clone of the branch:**
   - `setup.sh` then `start.sh` gives demo mode at http://127.0.0.1:8765.
   - `test.sh` is all green: 81 backend tests and 40 frontend tests, plus the build.
2. **Live, with your OK at that step:** `connect-router.sh` on Debian against your router.
   - **What it changes on the router:** it adds one more collector key to dropbear's `authorized_keys`, alongside
     Titan's. Your keys and Titan's key are kept, and the gate script is reinstalled, identical apart from the
     version.
   - **Then it's checked:** reads verified, an arbitrary command refused, and live mode on Debian.
   - **Afterwards:** you choose whether to keep that key or remove it with `router-remover`.
3. **The service:** `install-service.sh`, then reboot or log out and back in, and the dashboard is still up. Then
   `uninstall-service.sh` removes it.
4. **Windows unchanged:** the PowerShell scripts and tests still pass on Titan.

## Results (2026-11-22, Debian 13 x86_64, Wi-Fi on the router's LAN)
1. **Fresh copy in `~/cf-linux`:**
   - `setup.sh` created `.venv` and built the frontend on Debian's Node 20.19.2.
   - `test.sh` is all green: 81 backend tests (router-gate tests included), 40 frontend tests and the build.
   - `start.sh` serves demo mode, and a second `start.sh` reports "already running" and exits 0.
2. **`connect-router.sh`, live** (the owner typed the router password):
   - **Install:** Debian's own collector key was installed next to Titan's.
   - **Checks:** `verify` gives "SSH authentication and all seven read commands verified" (Cisco Meraki MX64), and
     `verify-locked` confirms the key refuses other commands.
   - **Live dashboard on Debian:** verified, with 21 clients and 5 ports, matching Titan's 21 clients at the same time.
     Titan's dashboard kept working.
3. **The service:**
   - `install-service.sh` starts the unit (active, `/api/health` ok), and re-running it is safe.
   - `uninstall-service.sh` stops and removes it.
   - **Not tested:** survival across a reboot. It needs `loginctl enable-linger`, which the script only suggests
     because it requires sudo.
4. **Syntax:** all six scripts pass `sh -n` and `dash -n`. `shellcheck` isn't installed on the test machine.

## Out of scope
- **CF Dashboard Plus on Linux:** its `install.sh` and a Linux toast channel are a separate add-on change after this.
  The add-on code already runs on Linux; only its installer and the Windows-only desktop notification would need
  work.
- **macOS:** likely works with the same scripts, but untested, so it's not claimed.
- Packages (`.deb`) and Docker images.

## Decisions for you
- **D1. The background service (L2):** include it now (recommended, since it's cheap and fits an always-on box) or
  later.
- **D2. The live router test (Testing step 2):** do it, which means one more collector key on the router during the
  test (recommended, because that's the only way to prove `connect-router.sh` works), or test in demo mode only.
